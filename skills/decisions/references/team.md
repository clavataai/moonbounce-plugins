# Build a decision with a team

One agent that writes the cases, labels them, writes the structure and scores it will pass its own test: it imagines a world, then fits that world. The team splits those jobs across subagents with separate contexts, so the structure is tested against cases its author never shaped, the way one agent writing tests and another making them pass beats one agent doing both. The adversaries are the **red team**, which attacks each version in the open, and the **judge**, which holds a **sealed** set that nobody else sees and that is scored once, at the end.

The barriers are instructions, paths and keys, not access control. They hold only if every role is a fresh subagent briefed with the paths it may read; a fork inherits the orchestrator's context, so no role runs as a fork. The judge is one subagent continued across the whole loop (SendMessage), never respawned, since only it knows where the sealed cases are. The loop runs on a test key. Only the judge and the orchestrator hold a production key, since one can read stored production content and its feedback.

## Roles

| Role | Job | Reads | Writes | Moonbounce calls |
| --- | --- | --- | --- | --- |
| **Orchestrator** (you) | Writes the brief and the objective with the person, routes paths, takes brief questions to the person, ships. Does no role's work. | The person, `brief.md`, `disagreements.md`, scorecards, `final.json` | `brief.md`, the decision file's `objective` | Discovery; on the test key after the first registration, `set_objective` and `set_binding`; at Ship, `register_structure`, `set_binding`, `set_objective`, `import_seeds` |
| **Case writer** | Real cases first, then synthetic ones, each with an intended label kept apart from the case. | `brief.md`, the real-case file | `cases.jsonl`, `intended.jsonl` | None |
| **Blind labeler** | Labels every case, red-team cases included, from the brief alone. | `brief.md`, one cases file | `labels.jsonl`, `red-<n>.labels.jsonl` | None |
| **Author** | Writes and revises the structure. | `brief.md`, `train.jsonl`, published red rounds, scorecards | The decision file's `structure`, `notes.md` | Test key: `hash_structure`, `register_structure`, dry-run `evaluate`, and `evaluate_batch` with `cost_report` on train and the published red rounds |
| **Red team** | Writes cases meant to break the current version, with intended labels. | `brief.md`, the decision file, `train.jsonl` | `red-<n>.cases.jsonl`, `red-<n>.intended.jsonl` | None |
| **Judge** | Seals the split, screens red cases, writes disagreements, scores each version, gives verdicts, scores the sealed set once. The only reader of the sealed folder. | Everything | The real-case file, `disagreements.md`, `red-<n>.screened.jsonl`, `train.jsonl`, published red rounds, scorecards, `final.json`, the sealed folder | Test key: `evaluate_batch` and `cost_report`. On a live decision, production: the feedback export only |

The **light team** is the case writer, the author and the judge: no labeler (the intended labels are the labels), no red team, at most two versions, and scorecards without `red`. It stops when train meets the target or the second version is done. Use it for a draft or a low-stakes decision with two outcomes. Use the full team when a wrong outcome costs money, access or safety, when there are more than two outcomes or any attributes, when the brief is in dispute, or before the decision serves production traffic.

## Files

Three places. The judge's **sealed folder** is its own `mktemp -d`, whose path it never passes on; it holds the sealed cases, the split's salt and the judge's scripts. **Staging**, outside the caller's repo (for example `$TMPDIR/moonbounce-team/<decision_id>/`), holds the real-case file, `cases.jsonl`, `intended.jsonl`, `labels.jsonl`, `disagreements.md` and unpublished red files; once it seals, the judge moves every sealed line out of staging into the sealed folder. The repo's `moonbounce/team/<decision_id>/` holds only what the author may read: `brief.md`, `train.jsonl`, published red rounds, scorecards, `final.json` and `notes.md`. Nothing sealed enters the repo, so neither a search nor git history can reach it.

- **The decision file**, `moonbounce/<decision_id>.json`: `{decision_id, structure, objective}`. The author writes `structure`; you write `objective` with the person ([Set the objective](tasks.md#set-the-objective)): which mistakes matter and how much (`mistakes`, by severity), the safe outcome (`fallback`), hard caps (`limits`) and the `target` cost per case. Every score in the loop is priced by it.
- **`brief.md`**: the outcomes with one-line definitions; the costs of mistakes in the person's words, as written into the objective (deny when it should grant, and so on); the target as cost per case; what `escalate` or an abstention means; in and out of scope; the `state` keys and attribute values the app sends, and which can be missing; the real example sources; a checklist of case kinds (boundary, hard negative, paraphrase twin, missing field, out of scope, noisy input).
- **`cases.jsonl`** and **`red-<n>.cases.jsonl`**: `{case_id, group, state, attribute_values?}`, plus `source: "real" | "synthetic"` and `kind` in `cases.jsonl`. `group` ties paraphrase twins together so they land on one side of the split. **`intended.jsonl`** and **`red-<n>.intended.jsonl`**: `{case_id, label, reason}`, plus `attack` for red cases, so the labeler never sees what a case was built to do. **`red-<n>.screened.jsonl`**: the judge's copy of the round without the cases it held back (those stay in the sealed folder), the only red file the labeler reads. **`labels.jsonl`** and **`red-<n>.labels.jsonl`**: `{case_id, label, unsure, reason}`. **`disagreements.md`**: each case where the labels differ or the labeler was unsure, with both reasons.
- **`train.jsonl`**, sealed cases and **published `red-<n>.jsonl`**: `{case_id, group, state, attribute_values?, label, label_source}`, plus `attack` for red. `label_source` is `human` when the person gave or settled the label, and `synthetic` when the case writer and the blind labeler agreed on it.
- **`scorecard-<n>.json`**: `{version, structure_hash, environment, binding, effective_hash, train: {n, cost_per_case, target_met, wrong}, red: {n, cost_per_case, wrong, by_attack, cases}, earlier_red: {n, cost_per_case, wrong}, comparison: {accepted, reasons, base_version}, leakage, verdict: "accept" | "reject"}`, the numbers copied from `cost_report` (`effective_hash` is its `objective.effective_hash`). **`final.json`**: `{version, structure_hash, environment, binding, effective_hash, sealed: {n, runs: [{cost_per_case, wrong}], cost_per_case: [lowest, highest]}, leakage}`.

## Scoring

The judge scores a version on a set of cases (train, a red round, the sealed set) with `evaluate_batch` and `cost_report` on the test key, never by hand:

1. `evaluate_batch` with the version's structure inline (`structure`) or by `structure_hash`, and up to 200 items a call: each case as `{item_id: case_id, state, attribute_values?, expected: label, label_source}`. In MCP the request goes under `body`. Keep each `batch_id`; batches expire after a day.
2. `cost_report` with those `batch_ids` as `candidate` (and a `base`, for a comparison). The results never pass through the judge's context. Page through the costliest cases with `cases: {filter: {kind: "wrong"}}` (or `severe`, `missing_criterion`, `{kind: "question", question}`, `{kind: "near_cut", at}`) for the scorecard.

Case ids are `item_id`s, and one side of a `cost_report` can't hold the same id twice, so keep `case_id`s unique across `train.jsonl`, the red rounds and the sealed set (prefix red ids with `red-<n>-`).

`cost_report` prices every mistake by the objective stored on the test key; without one it falls back to balanced costs, so store the objective before the first scoring, and compare only reports with the same `objective.effective_hash`. An abstention counts as its `abstain` outcome or, when the result names none, as its dearest mistake. A case the version fails permanently (content it can't read, an engine refusal) is priced as its dearest mistake. A retryable failure is left out (`excluded.failed_transient`): resend those items in a new `evaluate_batch` call and list both batches. [Score a dataset](tasks.md#score-a-dataset) has the request shapes.

## Loop

1. **Brief.** You write `brief.md` with the person, and write the mistake costs, fallback, limits and target into the decision file's `objective`. Store it on the test key (`set_objective`, after the first registration creates the decision) before the first scoring. On a live decision the judge builds the real-case file from the feedback export (REST `GET /v1/decisions/{decision_id}/feedback` with a production key; it is not an MCP tool). Done when every item in `brief.md` has an answer from the person or a source they named, and the objective says what each costly mistake costs.
2. **Cases.** The case writer writes 60 to 80 cases into staging, from the real-case file first and marking the rest synthetic, covering every checklist kind. Done when each kind has cases and every case has an intended label.
3. **Blind labels.** The labeler labels from the brief and the judge writes `disagreements.md`. Each disagreement, and each case the labeler marks unsure, is ambiguity in the brief, not noise: take it to the person, update the brief or drop the case, and never average the two labels. Same-model writers and labelers rarely disagree outright, so the unsure cases carry most of the signal. When the brief changes, both label sources re-check the labels they wrote before the change. Done when no disagreement is open and every unsure case has been taken to the person once.
4. **Seal.** The judge picks a random salt, saves it in the sealed folder, ranks groups by `sha256(salt + group)`, and seals the lowest-ranked groups until they hold at least 30% of the cases, at least 15 cases and at least 10 groups. Groups the person saw in step 3 stay in training. If that can't be met with training left twice the sealed size, the case writer writes more cases first. The judge writes `train.jsonl` to the repo. Done when the sealed and training cases share no group.
5. **Version.** The author writes the structure from the brief, `train.jsonl` and the published red rounds, registers it on the test key, checks it there (a dry-run `evaluate` for one case, `evaluate_batch` and `cost_report` for train), and writes its reasoning in `notes.md`. The first registration creates the decision and its test binding from the deployment's default; before the first dry run you set the binding (`set_binding`) to the engine and model production will run, and store the objective.
6. **Attack.** The red team writes `red-<n>.cases.jsonl` and `red-<n>.intended.jsonl` against that version: paraphrases, distribution shift, boundary values, missing fields the brief allows, out-of-scope inputs. Run it on a different model or vendor from the author's whenever one is available, and record which model each role ran on; a read-only CLI writes to stdout, so capture it into staging. The judge screens the round first, holds back any case that paraphrases a sealed one (held-back cases are never scored), and writes `red-<n>.screened.jsonl`. The labeler then labels that file blind, and disagreements and unsure cases go through step 3.
7. **Score.** The judge scores the version ([Scoring](#scoring)) on train, the current red round and every earlier published round, writes the scorecard, and publishes the round with its agreed labels. Until one version is accepted, a version is accepted if train's `target_met` is true; with no `target` in the objective, the person decides from the cost per case. After that, the judge runs one `cost_report` with the version's train and earlier-round batches as `candidate` and the last accepted version's batches on the same cases as `base`, first scoring that version on any of those cases whose batch has expired or that it never ran. The version is accepted when `accepted` is true (lower cost per case, every limit kept, no new severe mistake on a human-labeled case) and, since most of the team's labels are synthetic, no case the base got right is now one of the objective's severe mistakes, whatever its label: page the report's severe cases (`cases: {filter: {kind: "severe"}}`) and reject when any row's `base.severe` is false. The current round is reported, not gated on, since it was written to break that version. The next version starts from the last accepted one or the rejected one, as the author judges. Return to step 5.
8. **Stop** when the latest red round, from a model other than the author's and written against an accepted version, gets nothing wrong, or when three versions are done (two on the light team). An open brief question pauses the loop: the person answers, the brief and labels are updated, and the loop resumes. A brief change after sealing moves the sealed groups it touches to training (if that drops the sealed set below step 4's floors, the case writer writes fresh cases and the judge seals them), and earlier scorecards no longer count until the judge re-scores the latest version. The final version is the latest accepted one; if none was accepted, report to the person first. The judge scores it on the sealed set in one scoring of two runs (two `evaluate_batch` calls, each priced by its own `cost_report`) and writes `final.json`. If it misses the target, report that to the person before shipping. Never revise against the sealed set.
9. **Ship.** Ship the structure whose hash is in `final.json`: if the decision file has moved on, read that version back with `get_structure` on the test key. Register it in the environment you will run in, check the returned hash against `final.json`, set that environment's binding to the tested engine and model, store the decision file's objective there (`set_objective`; `unknown_outcomes` must be empty), and confirm the engine on one dry run. Put the decision file, structure and objective, in the caller's code. On a new decision, seed train, the published red rounds, the held-back red cases and the now-spent sealed set with `import_seeds`: `item_id` is the `case_id`, every label must be an outcome the result can produce, and batches hold at most 200. A batch is all or nothing: leave out cases that 400, and resend in smaller batches after a 502 or 422. On a decision that already has reviewed production traffic, seed them only on the test key (see below). Then route production items to owner and reviewer review. The next rework starts a fresh sealed set. The sealed score is a starting estimate; the real test is the blind spot checks reviewers answer on production traffic after the version ships.

## Rules that keep the barriers

- **The sealed set is scored once,** on the final version. It never informs a revision: the author learns from train and the open red rounds only. A sealed case the judge has to describe moves to training with its group.
- **Platform previews and suggestions are for after Ship.** On a production key, `preview` and `generate_suggestion` list the production cases that changed, and `get_evaluation` returns stored content, so the build loop makes none of these calls. Suggestions come after Ship, from real feedback ([Ask for suggestions](tasks.md#ask-for-suggestions)); the build loop has no seeded cases for them to learn from.
- **Agent labels are seeds.** `import_seeds` puts a new group in the `seed` split, weakest evidence. A seed whose `item_id` or normalized state text matches an existing group joins it and keeps that group's split. A decision with reviewed production traffic gets the team's seeds on the test key only, so the agent's labels never sit among the real cases its production previews and suggestions learn from. `source: "owner"` carries only the person's own judgment, on primary evaluations after Ship; during the loop their answers update the brief.
- **Sealed cases stay local.** They reach Moonbounce only through `evaluate_batch`, which stores usage, and for a day a batch under a `batch_id`; nothing feedback can attach to. The batch keeps the version's structure and, per item, the label, answers, outcome and resolved attribute values, never the `state`. The judge keeps the sealed batches' ids in the sealed folder and passes them to no one, since `cost_report` reads any batch in the environment by its id.
- **Reads match the app.** A question's `reads` names only paths the app always sends; read an optional field through its parent. A missing read path, or a missing attribute without a `default`, is a 400 `CONTENT_INVALID`, so missing-field cases leave out only what the brief says can be missing.
- **Leakage check.** Each scorecard flags question text that copies distinctive phrases from training or red cases. Matches against sealed cases are counted only in `final.json`, since a running count would tell the author which wording the sealed set holds.
- **Noise.** Engines answer the same case differently from run to run. When a verdict hinges on one or two cases, the judge runs the sets twice; small sets are indicative only.
- **Different priors.** Same-model agents share blind spots: a red team on the author's model can pass a structure that another model's red team breaks on most cases. When only one model is available, say so in the report.
- **Inline structures.** A dry-run `evaluate` takes the structure's fields (`questions`, `attributes`, `aggregations`, `result`) at the top level beside `state`; nesting them under `structure` is a 400. `evaluate_batch` is the other way round: the whole structure goes under `structure`, beside `items`.

## Role prompts

Give each subagent its prompt, the paths it may read, the path it writes and that file's shape from Files. Paste paths, never the contents of a file that role may not read. Never give any role but the judge the sealed folder's path.

- **Case writer.** "Write cases for the decision described in `<brief>`. Use the real cases in `<real-case file>` first; mark everything else `synthetic`. Cover every case kind in the brief's checklist, with paraphrase twins sharing a `group`. Use only the `state` keys and attribute values the brief says the app sends. Write each case to `<cases>` and its intended label and reason to `<intended>`, never in the case itself. Read nothing else."
- **Blind labeler.** "Label each case in `<cases>` using only `<brief>`. For each, give the outcome, whether you are unsure, and a one-line reason citing the brief. When the brief does not settle a case, mark it unsure and say what it is missing. Write `<labels>`."
- **Author.** "Write the structure for the decision in `<brief>` at `<decision file>`, using `<train>` and the published red rounds. State the brief's criteria in each question rather than wording drawn from particular cases. Read only paths the brief says the app always sends. Register each version on the test key, then check it there: a dry-run `evaluate` (the structure's fields at the top level of the body) for one case, `evaluate_batch` and `cost_report` over `<train>`. Never use a production key. After registering the first version, stop until you're told the binding and objective are set. Write `notes.md` with why each question, rule and cut is there."
- **Red team.** "Break the structure in `<decision file>` for the decision in `<brief>`. Write cases it gets wrong: paraphrases, shifted distributions, boundary values, missing fields the brief allows, out-of-scope inputs, messages mixing issues. Use the brief, not the structure, to decide each case's right outcome. Write cases to `<red cases>` and the attack, intended label and reason to `<red intended>`."
- **Judge.** "You hold the sealed folder; never give its path or a sealed case's content to anyone. Seal the split by salted hash (Loop step 4). Write `disagreements.md` from the intended labels and the blind labels. Screen each red round before labeling: hold back paraphrases of sealed cases in the sealed folder and write `red-<n>.screened.jsonl` for the labeler. Score each version on the test key with `evaluate_batch` and `cost_report` (Scoring) on train, the current red round and the earlier published rounds, keeping the sealed batches' ids in the sealed folder; give a verdict by Loop step 7; check leakage against training and red cases; write `<scorecard>`; publish the scored round. When the brief changes after sealing, move the sealed groups it touches to training. When told a version is final, score it on the sealed set in two runs and write `final.json`."
