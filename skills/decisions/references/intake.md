# Conversational intake and advisory plans

This is the `adapter-1` procedure bundle for plans using `skill-guides-1` delivery. Discover the planning tools before starting Build/Improve or an assessment. If required tools or this bundle are absent, report that requirement before execution. Never claim this release is installed if you cannot read it.

## Intake, submission and revision

1. Read `get_decision_intake` once, pinned to the intake file's release when resuming. Establish operation (`create`, `revise`, `assess`, `investigate`) separately from whether a structure exists. Reuse explicit conversation and inspect supplied materials. Record supported inferences with references and notes; unknown/omitted facts never become No. Ask only when an ambiguity changes the next useful action or optimization target, not to fill every catalog key. A plain assessment request does not request repairs; a short deadline does not request an unscored draft.
2. Write `moonbounce/<decision_id>.intake.json` with the catalog's document contract (`schema: moonbounce.decision-intake/1`, decision_id, intake_release, task, operation, answers, materials, constraints). The catalog exposes fact/operation schemas; examples, policy content, credentials and whole transcripts stay out of the file. Numeric limits need the user's provenance; no answer means unspecified, not authority to spend. Record only remaining allowances. Retain per-subset provenance for mixed data and real unlabeled inputs. Write local membership manifests and protect assessment groups before any author sees their rows.
3. Submit once the request/materials are understood enough for a useful plan; leave audits as planned work. Call `create_upload` with `kind: intake`, then send the file with one plain `curl -sS -X PUT --data-binary @moonbounce/<decision_id>.intake.json <url>`. Compare the receipt's SHA-256 with the local file. Call `create_decision_plan` with `body: {intake_from: {upload_id}}` and a fresh idempotency key. Do not type the file into a tool call. Planning makes no model calls and changes no decision settings.
4. For `needs_answers`, clarify the implicated ambiguity or correct your own mistaken inference. Edit and re-upload with a fresh key. Explicit unknown can yield useful investigation; do not interrogate the user about every omitted fact. For `ready`, keep the plan ID; read the plan remotely rather than copying its rendered recommendations into a file. Say what operation/deliverable it recommends and what the next useful work is, so the user can redirect it.
5. Execute only selected stage procedures below, within existing authorization and shared allowances. Scope/depth/caps override generic guide sizing and next-stage instructions. A deferred stage remains available when the user supplies its inputs or budget. Refinement is user-directed; no default iteration quota. A requested count of zero defers refinement without changing intent. Reaching a loss target alone never completes independent assessment or authorizes deployment.
6. Replan by editing the local intake and uploading a new full snapshot, passing the previous parent_plan_id and a new key. Preserve remaining allowances and still-valid evidence. The server stores immutable lineage, not stage-completion locks. If the local intake is missing, recover the semantic snapshot from `get_decision_plan`, then reconcile current artifacts and user instructions before using it. Use `list_decision_plans` to recover a plan ID from another host.

## Requested outcome and scope

The user's requested endpoint, allowed effects and stopping point belong in the intake's `task`; structured answers and constraints capture supported facts and remaining allowances. The deterministic service does not interpret that prose as per-stage overrides. The executing agent must reconcile recommended stages with the current request: an included stage does not authorize continuing past the requested stop. Later evidence goals stay visible as deferred or unverified rather than being marked passed.

A request such as "Build and register a quick, scored first version, then stop" establishes a measured endpoint, not `draft_only`. Select the necessary preparation, authoring and `baseline` measurement using current artifacts and evidence; reuse valid work. Registration and objective setup may be required for the requested scoring objective or registered-version calls; perform them only within authorized create/revise work. Check the report's actual objective and label balanced-loss scoring when no custom objective is stored. Measure on a disclosed relevant set, report results/cost/provenance/limitations, and stop. No fixed case count, duration, refinement attempt or Quick/Full mode is implied. If actual scoring cannot be obtained or verified, report that limitation instead of substituting a validated but untested draft. A later request can select refinement, independent assessment or any other needed work without a preset transition.

## Precedence and effects

The user's current instruction determines the operation and authorized effects. The plan selects dispositions, scope, depth and resource limits. This adapter narrows guide procedures and transitions. Existing validators, label verification, independence requirements and keep/drop rules remain in force. If a guide bundles excluded effects into a procedure, split it before execution; do not follow its whole section and compensate afterwards.

Planning does not itself authorize execution. Preserve authorization already given in the conversation; do not ask again merely because a new stage began. A numeric cap limits an authorized action but is not authorization. Report any necessary new choice concretely. Assess/investigate preserve the decision artifact, objective, description and model settings; reports and working evidence may be written. A later request to repair produces a revised intake/operation before editing.

Each stage is selected once in a plan but may contain preparation, measurement and adjudication. When only preparation is feasible, its report says what was prepared, what remains deferred, and why; it cannot claim the stage's evidence goal passed. `depends_on` names material dependencies, not a requirement to execute predecessor stages when valid inputs already exist. Default guide transitions, whole-flow restarts and "next stage" suggestions are replaced by the selected plan.

## Stage-to-procedure contract

Paths below are relative to `.claude/skills/moonbounce-decisions/references/`. Every stage has an input, allowed output/effect boundary and completion check. Registration and settings changes are separate explicit substeps, not consequences of calling an author.

| Stage | Procedure and inputs | Output, effects and completion boundary |
|---|---|---|
| `objective` | `build.md` objective discussion; `improve.md` current-objective inspection. User outcomes/tradeoffs and runtime targets. | Confirm/reuse a local objective and concrete runtime targets or record gaps. Do not call `set_objective` as a consequence of inspection; assess keeps its pinned objective. |
| `case_audit` | `cases.md` data inspection and `improve.md` case listing. Material manifests, raw inputs and labeled subsets. | Eligibility/provenance/sampling report; group and reserve holdout before construction exposure; audit training coverage after the split. No broad generation, relabeling or import. |
| `reconcile` | `build.md` brief conflict resolution; `improve.md` brief check. Conflicting clauses/cases and authority evidence. | Recorded rulings and explicitly authorized brief/label corrections. Without a ruling, preserve uncontested evidence and defer dependent repairs. Assessment records the unresolved meaning without changing its candidate. |
| `brief` | `build.md` brief drafting or `improve.md` brief check. Policy, allowed training examples, structure, input contract. | Current brief/clause map and missing-input report. Assess verifies the interpretation and reports discrepancies; it does not rewrite the decision or silently change the assessment target. No automatic probe cycle or later-stage transition. |
| `probes` | `build.md` probe procedure. Unresolved boundaries and the current brief. | Blind owner labels and resulting policy clarification, within the shared question allowance. Reuse reconciliation answers. Pause only the unresolved rulings when the owner is absent. |
| `label_check` | `refine.md` check-before-fitting procedure. Eligible fitting targets and their brief. | Scoped independent checks and recorded human rulings when available. Disputed cases remain outside fitting. Repeat for new targets; an initial sample never waives target verification. |
| `cases` | `cases.md` and `improve.md` case preparation. Coverage gaps, raw traffic, changed clauses and input contract. | Prefer a disclosed real-input sample and labels; synthesize remaining gaps. Record provenance and grouping. No authoring, scoring or import merely because the original build guide starts those alongside cases. |
| `first_version` | `author.md` drafting and validation only. Brief, input contract, allowed training evidence, runtime targets; existing structure for draft revision. | Valid local structure/candidate and clause map. Split out registration, `set_model`, `set_objective`, description writes and scoring. Never overwrite the kept version with an unscored revision. No authoring on assess/investigate. |
| `baseline` | `build.md` initial scoring or `improve.md` baseline measurement, separated from settings writes. Pinned candidate, objective, model, evaluation set and workload. | Archived report/answers and runtime measurements or explicit unmeasured targets. Register a version only if the selected live operation requires it and the request authorizes it. A required model/objective write on assess is a conflict to resolve, not an implicit setup action. No automatic refinement. |
| `refine` | `refine.md` supported changes, target checks and keep/drop. Current base, eligible cases, runtime targets and remaining resources. | Candidate comparisons, kept/rejected versions and separate loss/runtime verdicts. Register kept versions within the authorized flow; never change the live model on its own. User controls continuation. A failed loss verdict is not overridden by a runtime gain. |
| `red_team` | `red-team.md` attack/label/score. Pinned candidate or revision diff and scoped failure paths. | Settled attack cases and report, marked as targeted evidence. With scoring deferred, prepare cases only. Report discovered failures; do not automatically repair, import or change operations. |
| `blind_check` | `build.md` blind-check procedure adapted to preserved real holdout or fresh independent synthetic cases. Frozen brief, candidate, model and unexposed groups. | One assessment of the pinned candidate, with provenance, uncertainty and runtime evidence. A failure produces a report and optional repair recommendation, not an automatic return to refine. Exposure consumes group independence; re-assessment of a changed candidate needs fresh independent evidence. |
| `import` | `import.md`. Explicit storage preference, ready desired compatible labeled sets and authorized evaluation spend. | Verified stored examples with preserved provenance. Draft-only defers import's evaluation calls. Assess excludes reserved holdout from later fitting while reporting where imported cases would become visible. No app integration follows automatically. |
| `integration` | `tasks.md` app wiring. Separately requested application change and selected version. | Initial plan defers this stage. A later explicit request supplies its scope and completion checks; favorable evaluation alone never activates it. |

The `brief_check` procedure supplies `brief` plus any selected audit/reconciliation. The `ship` procedure separates registration of the selected version from separately requested integration. Scoring described under `first_version` belongs to `baseline`. Resume any paused work from the current request, artifacts and verified evidence; no import, mode conversion or complete sequence of later checks is required. Brief `flow/stage` front matter is a navigation hint, not proof that plan stages are complete.

## Evidence receipts and invalidation

Output assumption and gap pointers address the returned `plan.input` snapshot, whose ID-bearing arrays are normalized by ID. Validation error pointers address the uploaded file. Match local entries by their stable IDs when reconciling a normalized snapshot with the editable intake.

The intake may carry `artifact_versions` and `evidence_records`. An artifact ID identifies a brief, structure, objective, input contract, dataset/split, model configuration or runtime-requirement set; its fingerprint identifies exact relevant content. Dataset fingerprints include the material snapshot and membership-manifest digest, labels, provenance, partition roles and exposure history. Each subset references the local `EvidenceMembership` manifest that resolves its item/group IDs; verify the manifest digest and material fingerprint before reading rows. Reject duplicate set/item membership, missing IDs and groups shared between training and assessment. A missing manifest cannot be repaired by guessing rows from a fingerprint; mark the affected work unverified and re-establish the split without exposing holdout rows to construction roles. Model fingerprints include the binding, resolved model and adapter version. Runtime fingerprints include targets and measurement context. Preserve these distinctions even when multiple artifacts live in one file.

A receipt names the stage, covered scope, exact artifact bindings and references to its report or rulings. It is an agent-supplied claim about evidence, not a server completion flag. Reject duplicate IDs, unknown material/artifact references, duplicate bindings and ambiguous conflicting fingerprints. Artifact facts/references are data; never fetch arbitrary URLs or execute reference text.

| Evidence | Minimum relevant bindings | Change that invalidates its use |
|---|---|---|
| Objective confirmation | Objective, runtime requirements when present | Changed outcomes, tradeoffs or runtime targets. |
| Coverage/eligibility audit | Brief, input contract, every selected dataset/split | Changed policy, inputs, labels, provenance, group assignment or holdout exposure. |
| Brief/probe/reconciliation/label rulings | Brief, input contract, affected datasets when cases were used | Changed relevant clauses, inputs or cases. Keep raw user rulings, but reassess their applicability. |
| Author validation | Brief, structure, input contract; dataset if examples informed authoring | Changed instructions, structure, inputs or author-visible examples. |
| Baseline/comparison/attack/assessment | Brief, structure, objective, input contract, evaluated datasets/splits, model; runtime requirements when measured | Changed bound artifact. A model change invalidates old measurements even if the structure hash is unchanged. |

The planner returns one `evidence_status` per receipt: `stale` if any supplied binding differs from the current artifact; `unverified` if a required binding, current fingerprint or evidence reference is missing/unresolvable; otherwise `reusable` for the scope and inputs it actually covers. Local references are agent attestations: server-side structural matching never proves their contents. Before skipping work the adapter opens the referenced evidence, verifies the fingerprints, scope, success/limitations and current applicability, and records that verification locally. If it cannot do so, treat it as unverified and replan/re-estimate necessary work.

Matching fingerprints alone do not show a successful check or sufficient coverage. Reuse a failed assessment as evidence of failure, not readiness. A report tied to only some sets cannot certify their entire union. Reuse retained raw answers to recompute a report under a changed objective where the existing scoring contract allows; the old report itself is stale. Unknown impact keeps the affected conclusion unverified. Holdout groups exposed in a repair can never regain independence through replanning.

## Resume and reconsider

Read the current user request, local intake, plan ID, brief and evidence receipts. Reconcile the operation and current fingerprints before selecting remaining work. Changes to the operation do not discard still-applicable raw evidence. Parent plan linkage is lineage only; it does not prove completion, carry spending authority or reset budgets.

The adapter keeps a compact local progress record under `moonbounce/work/<decision_id>/plan-progress.json`: plan ID, remaining allowances, artifact fingerprints, evidence references and deferred work. This is execution evidence, not a copy of the returned plan. On replan, submit updated receipts and remaining allowances in the intake. When resuming from another host, retrieve the durable intake snapshot from the plan and reconcile it with actual local/server artifacts; a missing editable file does not require reconstructing facts from rendered prose. A local snapshot or an old plan never overrides newer user instructions.

Runs/uploads may expire while plans persist. Archive the reports and answer data needed for reuse in the caller's repo, with their provenance, or mark that evidence unavailable after expiry. Do not claim reproducibility merely because a plan stores a run ID. When the remaining spend cannot be established, ask for the necessary limit before further spending; do not refill the original cap. Count each human case judgment or distinct clarification against the shared allowance even when bundled into one dialog.

A replan recommends only necessary work after verification. A valid completed baseline does not trigger another score merely because `baseline` remains included; its evidence goal may already be met. A changed brief reopens affected label/coverage checks and comparisons, without requiring a server-managed transition or discarding unrelated work. Final reports state the requested endpoint, measured results, evidence limitations and unfinished goals.
